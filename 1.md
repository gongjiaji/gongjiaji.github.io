# Jumphost Maker/Checker Control System - MVP Specification

## 1. Goal

Build a maker/checker control layer for `nwsshdbs`.

Main goals:

1. Checker must be actively watching before maker can send commands to devices.
2. Checker can see maker device input output in real time.
3. Checker can pause, resume, stop, or rejoin a maker session.
4. Existing maker command audit remains in Graylog. The controller does not persist command audit or terminal output.
5. If all controllers are unavailable, maker falls back to the current existing flow.

This is an MVP design. Runtime state is stored in memory.

---

## 2. High-Level Architecture

### Single-controller MVP

```text
Maker Jumphost-01 ─┐
Maker Jumphost-02 ─┼── Control Server
Maker Jumphost-03 ─┘
```

Control server contains:

```text
- FastAPI backend
- Checker web UI
- In-memory runtime state
- SSE stream
```

No DB is required for MVP.

### Degraded two-controller mode

```text
Maker wrapper controller list:
1. control-01
2. control-02
```

Controllers do not share state.

If `control-01` is unavailable, maker tries `control-02`. Checker must start/rejoin CR on whichever controller maker is using.

### Future multi-controller HA mode

For future full HA:

```text
checker.dbs.com
    ↓
F5 HA Pair
    ↓
control-01 / control-02 / control-03
    ↓
Redis HA
```

Redis would hold runtime state and Pub/Sub terminal events.

---

## 3. Runtime State Scope

The MVP controller stores only runtime state in memory:

```text
- Active CRs
- Sessions
- CR-to-session index
- SSE subscribers
```

It does not persist:

```text
- Terminal output
- Command audit
- CR history
- Session history
```

Command audit already goes to Graylog.

If the controller restarts, all in-memory state is lost.

---

## 4. Roles

### Checker

Checker uses the controller web UI.

Checker can:

```text
- Start CR
- Close CR
- Watch all sessions under a CR
- Pause session
- Resume session
- Stop session
- Rejoin frozen session by session ID
```

Checker must authenticate through LDAP and must be in the L2 checker group.

LDAP implementation is out of scope for this spec. The application should expose clear hooks/placeholders for LDAP integration.

### Maker

Maker logs into a jumphost and runs `nwsshdbs`.

Maker flow:

```text
1. Run nwsshdbs
2. Input CR number
3. Input/select target device
4. Wrapper handshakes with controller
5. If allowed, maker enters controlled Paramiko device session
6. Every command is checked before sending to device
```

---

## 5. CR and Session Model

### CR

CR is an authorization container.

```text
CR active = maker can create sessions under this CR
CR closed/inactive = no new sessions; existing sessions stopped
```

CR number comes from an external CR system. The controller only tracks whether that CR number is active in this maker/checker system.

### Session

Session is the actual maker-to-device operation object.

A single CR can have multiple sessions:

```text
CR123456
├── session 4829 -> router01
├── session 0731 -> router02
└── session 9044 -> firewall01
```

Checker watches and controls sessions individually.

Rule:

```text
Same CR + same target_device can have only one active/paused/frozen session at a time.
```

---

## 6. Session ID

Session ID is a short number shown to maker during freeze/rejoin.

Final rule:

```text
Session ID = 4 digit random number
Examples: 4829, 0731, 9044
```

Generation rules:

```text
- Check against current in-memory sessions
- If collision, generate again
- Only needs to be unique within current controller memory
```

Example implementation:

```python
import random


def generate_session_id(existing_sessions: dict) -> str:
    for _ in range(100):
        session_id = f"{random.randint(0, 9999):04d}"
        if session_id not in existing_sessions:
            return session_id
    raise RuntimeError("Unable to generate unique session ID")
```

## 8. Session Lifecycle

### active

Normal controlled state.

```text
- Checker is watching
- CR is active
- Session is active
- Maker commands can be sent after can-execute check
```

### paused

Checker intentionally paused the session.

```text
- Maker command is blocked
- Paramiko connection stays open
- Only checker resume can return it to active
```

### frozen

Checker is not watching, or controller-side session needs rejoin.

```text
- Maker command is blocked
- Paramiko connection stays open
- Maker sees short session ID
- Any L2 checker can rejoin using the session ID
```

### stopped

Session cannot recover.

Caused by:

```text
- Checker stop
- CR close
- CR/session expiry
```

Maker next command:

```text
- Command is not sent
- Paramiko channel/client closes
- nwsshdbs exits
```

### ended

Maker exited normally or device session ended.

### failed

Device connection failed or wrapper error occurred.

---

## 9. State Transitions

```text
handshake success          -> active
checker pause              -> paused
checker resume             -> active
checker not watching       -> frozen
checker rejoin             -> active
checker stop               -> stopped
CR close                   -> all sessions stopped
maker normal exit          -> ended
device connection error    -> failed
24h expiry                 -> CR closed / sessions stopped
```

Rejoin is only allowed:

```text
frozen -> active
```

Rejoin is not allowed for:

```text
paused
stopped
ended
failed
CR closed/expired
```

## 10. Checker Watching Heartbeat

Checker is considered watching only when the CR page is visible.

Frontend rule:

```javascript
setInterval(() => {
  if (document.visibilityState === "visible") {
    fetch(`/api/cr/${crNumber}/heartbeat`, { method: "POST" })
  }
}, 3000)
```

Backend rule:

```text
heartbeat interval: 3 seconds
watching timeout: 10 seconds
```

If no heartbeat for more than 10 seconds:

```text
CHECKER_NOT_WATCHING
session becomes frozen
maker cannot send next command
```

If checker closes tab, switches tab, minimizes browser, sleeps machine, or network breaks, heartbeat stops.

## 11. Command-Before-Send Check

Every input that will be sent to the device must pass `can-execute` first.

Flow:

```text
maker enters command
    ↓
nwsshdbs detects command boundary
    ↓
POST /api/sessions/{session_id}/can-execute
    ↓
allowed=true  -> send to device
allowed=false -> block command
```

Strong rule:

```text
can-execute is the control point.
If can-execute fails, command must not be sent to device.
```

Recommended command send order:

```text
1. can-execute
2. chan.send(command)
3. send input event
```

Reason: if `chan.send` fails, checker should not see it as a successfully sent input.

## 12. Pause / Resume / Stop Semantics

### Pause

```text
pause = block next command, keep Paramiko connection
```

Maker sees:

```text
[PAUSED] Session paused by checker.
Command was not sent.

Please wait for checker to resume this session.
```

### Resume

```text
resume = session.status active again
```

Maker next can-execute succeeds if checker is watching.

### Stop

```text
stop = block next command, then terminate maker session
```

Maker sees:

```text
[STOPPED] Session stopped by checker.
Command was not sent.

Closing device connection...
Session terminated.
```

Paramiko handling:

```python
try:
    channel.close()
except Exception:
    pass

try:
    ssh_client.close()
except Exception:
    pass

raise SystemExit(1)
```

Do not use `os._exit(1)` unless the process is stuck and normal exit cannot work.

## 13. Freeze / Rejoin

### Freeze trigger

Freeze happens when:

```text
CHECKER_NOT_WATCHING
SESSION_FROZEN
controller session needs rejoin
```

Maker behavior:

```text
- Command is not sent
- Paramiko connection is kept open
- Session ID is displayed
- Maker tells checker the session ID manually
```

Maker screen:

```text
[PAUSED] Checker is not watching.
Command was not sent.

Rejoin Session ID: 4829

Please tell this Session ID to checker.
Checker should open the controller web page, click Rejoin, and enter this Session ID.
Waiting for checker to rejoin...
```

### Rejoin rule

Any L2 checker can rejoin if they know the session ID.

Rejoin conditions:

```text
- session exists
- session.status = frozen
- CR is still active
- checker is L2
```

After rejoin:

```text
session.status = active
checker_last_seen = now
```

Maker can continue on next command.

## 14. Controller Fallback and Emergency/Current Flow

Maker has a configured list of controllers:

```text
CONTROL_SERVERS=http://control-01:8000,http://control-02:8000
```

Startup behavior:

```text
1. Try control-01 /api/health
2. If ok, use control-01
3. If not ok/disabled/unreachable, try control-02
4. If none available, enter current/emergency flow
```

If controller is reachable but CR is not active:

```text
- Try next controller
- If no controller has active CR, tell maker CR is not active
```

### Important boundary

```text
CHECKER_NOT_WATCHING does not trigger emergency/current flow.
It freezes maker session.
```

Only when all controllers are unavailable:

```text
CONTROLLERS_UNAVAILABLE -> current/emergency flow
```

### Current/emergency flow

Emergency mode means fallback to the existing current flow.

```text
- No checker start CR requirement
- No controller session
- No live stream
- No pause/resume/stop
- Existing CR validation continues
- Existing Graylog command audit continues
```

If maker is already connected to a device and all controllers become unavailable:

```text
- Do not terminate Paramiko
- Continue current device session under current/emergency flow
```

Once in current/emergency flow, do not automatically return this device session to controlled mode.

Maker message:

```text
[EMERGENCY MODE]
All controllers are unavailable.
Maker/checker control is disabled.
Continuing with current CR flow.
All commands will continue to be audited.
```

## 15. Controller Restart / SESSION_NOT_FOUND

Because state is memory-only, controller restart clears sessions.

If maker calls `can-execute` and receives `SESSION_NOT_FOUND`:

```text
- Do not immediately close Paramiko
- Try to re-handshake with current CR + target
- If checker restarted CR, controlled mode can resume
- If CR not active, freeze/ask checker to start CR
- If all controllers unavailable, enter current/emergency flow
```

---

## 16. Target Device Rule

Handshake must include target device information.

Required fields:

```text
cr_number
maker
target_device
target_ip
session_type
```

Jumphost is not trusted from request body. Controller derives jumphost from API token.

Duplicate target rule:

```text
Same CR + target_device cannot have another active/paused/frozen session.
```

If duplicate:

```text
TARGET_ALREADY_IN_USE
```

## 17. Event Streaming

Maker sends events to controller:

```text
POST /api/sessions/{session_id}/events
```

Checker subscribes at CR level:

```text
GET /api/cr/{cr_number}/stream
```

Controller forwards events to current SSE subscribers only.

No persistence.

If no checker is subscribed, event is discarded.

### Event behavior

```text
input   = command was actually sent to device
output  = raw Paramiko channel.recv() output, not stripped
blocked = command attempted but blocked before device
system  = state/system message
error   = error message
```

Output event sending must not block maker terminal display.

Recommended:

```text
- os.write(stdout, data) immediately
- queue output event in background
- if output event fails, drop it
```

`can-execute` remains synchronous and mandatory.

## 19. Maker API Authentication

Each jumphost has its own API key.

Jumphost stores plaintext key in `.env`:

```env
CONTROL_API_KEY_ID="jh01"
CONTROL_API_KEY="..."
```

Requests include:

```http
X-Api-Key-Id: jh01
Authorization: Bearer <api_key>
```

Controller stores token hashes, not plaintext.

Validation:

```text
1. Use X-Api-Key-Id to find token hash
2. Hash Authorization token
3. Use constant-time compare
4. If matched, identify jumphost
```

Do not trust `jumphost` from request body.

## 21. Controller Internal Logic

### Start CR

```text
- Check checker is L2
- If CR already active, return CR_ALREADY_ACTIVE unless same checker refresh behavior is desired
- Save active_cr[cr_number]
- Set checker_last_seen = now
```

### Close CR

```text
- Mark CR closed
- Mark all sessions under CR stopped
- stop_reason = CR_CLOSED
```

### Heartbeat

```text
- Check checker is L2
- Update checker_last_seen
```

### Handshake

```text
1. Validate maker API key
2. Resolve jumphost from key
3. Check CR exists and active
4. Check checker_last_seen <= 10 seconds
5. Check same CR + target_device has no active/paused/frozen session
6. Generate 4 digit session ID
7. Create session active
8. Add to cr_sessions
9. Broadcast system event
```

### Can execute

Order:

```text
1. If session not found -> SESSION_NOT_FOUND
2. If CR missing/closed -> CR_CLOSED or CR_NOT_ACTIVE
3. If session paused -> SESSION_PAUSED
4. If session frozen -> SESSION_FROZEN
5. If session stopped -> SESSION_STOPPED
6. If session ended/failed -> SESSION_NOT_FOUND or SESSION_STOPPED
7. If checker heartbeat expired:
   - set session.status = frozen
   - return CHECKER_NOT_WATCHING
8. Else allowed = true
```

### Rejoin

```text
- Checker must be L2
- Session must exist
- Session must be frozen
- CR must be active
- Set session active
- Update checker_last_seen
- Broadcast system event
```

### Events

```text
- Validate maker API key
- Session must exist
- Build event envelope
- Broadcast to CR subscribers
- Do not persist
```

## 23. Cleanup Rules

24-hour rule:

```text
CR active longer than 24h -> CR closed/expired
Session older than 24h -> stopped/expired
```

Cleanup job frequency:

```text
every 5 minutes
```

Effects:

```text
CR_EXPIRED -> CR closed and all sessions stopped
SESSION_EXPIRED -> session stopped
```

Maker next command:

```text
- command blocked
- Paramiko closes
- nwsshdbs exits
```

```python
        ...
```

Existing `nwsshdbs` integration points:

```text
1. Program startup: select_controller()
2. After CR/target chosen: handshake()
3. Before every device input: can_execute()
4. After successful chan.send(command): send_event("input", command)
5. After channel.recv(): send_event("output", output_text)
6. If command blocked: send_event("blocked", command, reason)
7. On normal exit/error: end_session(reason)
```

Output event should be background/non-blocking.

## 26. Paramiko Output Mirroring

Use interactive shell:

```python
channel = ssh_client.invoke_shell(term="xterm", width=120, height=40)
```

When receiving output:

```python
data = channel.recv(1024 * 1024)
if not data:
    break

os.write(sys.stdout.fileno(), data)
client.send_event("output", data.decode(errors="ignore"))
```

Do not strip output.

This supports pagination such as `--More--` because checker receives the same output stream maker sees.

## 27. Runtime Mode

Controller uses FastAPI async app.

Production single-controller command:

```bash
gunicorn app.main:app \
  -k uvicorn.workers.UvicornWorker \
  -w 1 \
  -b 0.0.0.0:8000
```

Important:

```text
workers = 1
```

Reason:

```text
State is in memory. Multiple workers would have separate active_cr/session state.
```

Async endpoints are required for SSE and non-blocking request handling.

Avoid blocking operations in FastAPI endpoints:

```text
- time.sleep
- requests
- long CPU work
- blocking LDAP calls without threadpool
```

## 31. Critical Rules Summary

```text
1. Every command sent to device must pass can-execute.
2. CHECKER_NOT_WATCHING freezes maker; it does not trigger emergency/current flow.
3. Only all controllers unavailable triggers current/emergency flow.
4. Output event failure must not block maker terminal display.
5. can-execute allowed -> chan.send succeeds -> then send input event.
6. Rejoin is only for frozen sessions.
7. Any L2 checker can rejoin if they know the session ID.
8. CR close/expire stops all sessions and prevents rejoin.
9. Same CR + target_device cannot have multiple active/paused/frozen sessions.
10. Session ID is 4 random digits and must be unique in current controller memory.
11. Controller uses one worker only while state is in memory.
12. Once a device session enters current/emergency flow, do not automatically return it to controlled mode.
```
