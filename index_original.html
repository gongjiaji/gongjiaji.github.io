# Logging and Exception Handling Design ## 1. Overview This document defines a structured, local-first logging system with unified exception handling. Goals: - Enable fast debugging with clear error summaries and traceback - Ensure reliability with local file logging first - Support machine and AI analysis through structured logs - Minimize logging burden in business code --- ## 2. Design Principles - MUST use structured logs in JSONL format - MUST write logs to local files first - MUST NOT depend on external systems such as ELK at runtime - MUST centralize logging at framework boundaries - MUST NOT scatter logging across business logic - MUST make logs traceable through correlation IDs --- ## 3. Log Format - Format: JSONL (one JSON object per line) - No multiline logs - Traceback MUST be stored as a string field - Schema MUST remain consistent --- ## 4. Log Streams There are 5 log types: - `api_access` - `api_error` - `job_run` - `job_error` - `service` Each writes to its own file: api_access.jsonl api_error.jsonl job_run.jsonl job_error.jsonl service.jsonl --- ## 5. Correlation IDs ### request_id (API) - MUST exist for every API request - MUST reuse `X-Request-ID` header if provided - MUST generate a new one if not provided - MUST be included in: - api_access - api_error - response header ### run_id (Job) - MUST exist for every job execution - MUST be unique per execution - For current single-node deployment, use job start timestamp with second precision Example: 20260408-030501 Assumptions: - Single-node deployment - No same-second duplicate runs --- ## 6. API Logging ### Middleware Middleware MUST: - Generate or extract request_id - Record api_access - Measure latency - Attach X-Request-ID to response ### Global Exception Handler Global exception handling MUST: - Catch all uncaught exceptions - Record api_error - Return a unified error response - MUST NOT expose traceback to client - MUST include traceback in logs --- ## 7. Job Logging All jobs MUST run through a wrapper. Execution flow: start -> run -> success / error The wrapper MUST: - Generate run_id - Record job_run - Record job_error on failure - Measure execution duration --- ## 8. Service Logging service logging is used for: - Application startup and shutdown - Database or Redis status - Internal system events Notes: - No request_id required - No run_id required - Used for system-level observability --- ## 9. Error Log Design Each error log MUST include: - component (module name) - stage (execution step) - error_type - error_summary (short, human-readable) - exception (full traceback string) Principles: - Summary is for quick understanding - Traceback is for deep debugging --- ## 10. Log Rotation Since system logrotate may not be available: - MUST use application-level rotation - Use time-based rotation (daily) - MUST retain limited history (for example 30 days) - MUST automatically delete old logs --- ## 11. Security Logs MUST NOT contain: - passwords - tokens - authorization headers - sensitive personal data - large request bodies --- ## 12. Architecture Rules - MUST NOT rely on business code for logging structure - MUST NOT scatter try/except plus logging across the codebase Instead: - API logging must be handled by: - middleware - global exception handler - Job logging must be handled by: - wrapper Business code should only add contextual fields when needed. --- ## 13. Summary This system provides: - Structured JSONL logs - Separation by API / Job / Service - Traceability via request_id / run_id - Centralized logging architecture - Local-first logging with built-in rotation
