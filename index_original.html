# Logging and Exception Handling Design ## 1. Objective Implement a simple, reliable logging and exception handling system for a FastAPI service. Requirements: - Keep implementation simple (v1) - Logs must be easy for humans to read - Logs must support debugging quickly - Avoid scattered logging logic in business code - Centralize logging at framework level --- ## 2. Log Files There are only 3 log files: - api.log - job.log - service.log All logs are plain text (NOT JSON). --- ## 3. Log Levels - INFO → normal events (short, concise) - ERROR → failures (must include traceback) --- ## 4. API Logging ### 4.1 Middleware Responsibilities Implement a FastAPI middleware that: - Generates a `request_id` for every request - Stores it in `request.state.request_id` - Measures request latency - Writes access log to `api.log` Format: [request_id] METHOD PATH STATUS LATENCY_MS Example: [abc123] GET /api/review 200 45ms --- ### 4.2 Global Exception Handler Implement global exception handling: #### For Exception (critical) Must: - Catch ALL unhandled exceptions - Log as ERROR - Include: - request_id - method - path - error summary - full traceback Format: [request_id] METHOD PATH error_summary Traceback ... Example: [abc123] GET /api/review db timeout Traceback (most recent call last): ... Response: { "message": "Internal server error", "request_id": "abc123" } --- #### For HTTPException (expected errors) Log as WARNING or INFO. Example: [abc123] GET /api/user 404 User not found --- ### 4.3 request_id Rules - MUST generate for every request - MUST be included in ALL api logs - No need to require frontend to send it - SHOULD attach to response header (`X-Request-ID`) --- ## 5. Business Code Rules (API) ### DO NOT: - Add try/except everywhere - Log errors manually in every function ### DO: Only use try/except when: - Converting to business error (HTTPException) - Fallback logic (graceful degradation) - Adding useful business context Example: try: call_external_api() except TimeoutError: raise HTTPException(502, "Upstream timeout") --- ## 6. Job Logging Use APScheduler for scheduling. Implement a **job logging wrapper/helper**. --- ### 6.1 run_id Each job execution MUST have a run_id. Format: YYYYMMDD-HHMMSS Example: 20260408-030501 --- ### 6.2 Required Logging (Framework Level) Every job MUST log: #### Start [job_name][run_id] started #### Success [job_name][run_id] success duration=12.4s #### Failure [job_name][run_id] failed Traceback ... --- ### 6.3 Optional Business Logs (Per Job) Each job MAY log additional details depending on its logic. Examples: [sync_rules][20260408-030501] fetched 1200 rules [sync_rules][20260408-030501] processed 1190 success, 10 failed Another example: [daily_report][20260408-060000] generated report file report_20260408.csv --- ### 6.4 Wrapper Behavior The wrapper MUST: - Generate run_id - Log start - Execute job - Measure duration - Log success OR failure - Log traceback on failure --- ## 7. Service Logging `service.log` is ONLY for service lifecycle. Must log: service starting service started service startup failed service shutting down service stopped If startup fails: - MUST log full traceback Example: service starting service startup failed Traceback ... --- ## 8. Log Rotation Requirements: - Rotate logs DAILY - Keep current file name unchanged: - api.log - job.log - service.log - Archive old logs (e.g. api.log.2026-04-08) - Automatically delete old logs (housekeeping) Retention example: - Keep last 30 days --- ## 9. Implementation Notes - Use Python `logging` module - Use separate loggers or handlers per file: - api logger → api.log - job logger → job.log - service logger → service.log - Ensure thread-safe logging - Ensure no duplicate logs --- ## 10. Summary This system provides: - 3 log files only (simple) - Human-readable logs - request_id for API tracing - run_id for job tracing - Centralized exception handling - Minimal business code pollution - Daily rotation with cleanup --- ## 11. Deliverables (IMPORTANT) Claude Code MUST implement: 1. FastAPI middleware for: - request_id - access logging 2. Global exception handlers: - Exception - HTTPException 3. Logging setup: - api.log - job.log - service.log 4. Job logging wrapper: - run_id - start / success / failure 5. Log rotation: - daily rotation - retention cleanup 6. Example usage: - 1 API endpoint - 1 sample APScheduler job The implementation must be clean, minimal, and production-ready.
